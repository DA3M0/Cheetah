# Model registry — developer guide

This is the developer documentation for Cheetah's compile-time model registry:
how a model family declares itself (registration files), how `build.rs` turns
those declarations into the generated registry, how the engine selects a
backend, and how to add a new architecture, family, or backend.

For the memory manager and the native backend that most native registrations
point at, read [ANT_MEMORY.md](ANT_MEMORY.md) alongside this document.

---

## 1. Overview — three layers, one direction of dependency

```
src/chat/models/registrations/<family>.rs     ← declarative: WHAT exists
        │  (discovered + included by build.rs)
        ▼
OUT_DIR/model_registry.rs                     ← generated: REGISTRY, ALL_ARCHITECTURES
        │  (include! into src/chat/models/mod.rs)
        ▼
Engine::load / registry.rs                    ← selection: WHICH backend runs
```

Rules the design enforces:

- **Registration files contain no runtime code.** They are pure declarations
  (architectures, chat template, stop markers, backends table, family
  constants).
- **Runtime implementations live in sibling modules** (`src/chat/models/
  qwen2.rs`, `llama.rs`, … — Candle bridges; `native/` — the mmap backend;
  `vulkan_transformer.rs` — the Vulkan executor) and are declared manually in
  `src/chat/models/mod.rs`.
- **Adding a model = adding two files** (implementation + registration) plus
  a `mod` line; build.rs picks the registration up automatically. There is no
  central list to edit and no exclusion list in build.rs.

## 2. Build-time discovery and generation (`build.rs`)

### 2.1 Discovery

```rust
discover_registrations(Path::new("src/chat/models/registrations"))
```

- Scans **only** `src/chat/models/registrations/` for `*.rs`. The directory is
  the contract: every file contributes exactly one registration. There is no
  exclusion table (the earlier design scanned the whole `models/` directory
  and excluded infrastructure files by name — fragile).
- Filenames must be valid Rust identifiers; duplicates panic at build time.
- Results are **sorted by name** for a stable, platform-independent registry
  order.
- `cargo:rerun-if-changed` is emitted per file and for the directory.

Shaders are discovered separately (`discover_shaders`): the shared operator
shaders (`matmul.comp`, `matmul_bf16.comp`, `shared_ops.comp` at the repo
root) plus any `*.comp` file dropped into `src/chat/models/`. Under
`--features vulkan` they are compiled with `glslc` (override with the `GLSLC`
env var); the generated shader registry maps each name to the compiled `.spv`
path (or `None` when Vulkan was not compiled in).

### 2.2 Generated artifacts (`OUT_DIR/model_registry.rs`)

```
// @generated by build.rs from src/chat/models/registrations — do not edit.
#[path = ".../registrations/gemma.rs"] mod gemma_registration;
#[path = ".../registrations/llama.rs"] mod llama_registration;
...

pub(crate) const REGISTRY: &[&ModelRegistration] = &[
    &gemma_registration::REGISTRATION,
    ...
];

/// Every architecture name across all registrations, in registry order.
pub(crate) const ALL_ARCHITECTURES: &[&[&str]] = &[
    gemma_registration::ARCHITECTURES,
    ...
];
```

- Module names get a `_registration` suffix to avoid colliding with the
  implementation modules declared in `mod.rs`.
- Each registration file exports `ARCHITECTURES` so the generated
  `ALL_ARCHITECTURES` index can be assembled without runtime work; a test
  (`all_architectures_index_covers_the_registry`) asserts the index and the
  registry stay consistent in both directions.
- `include!(concat!(env!("OUT_DIR"), "/model_registry.rs"))` inside
  `src/chat/models/mod.rs` wires everything into the module tree (generated
  modules are children of `models`, so registration files reach
  implementations via `super::qwen2::load` etc.).

## 3. `ModelRegistration` schema

```rust
pub(super) struct ModelRegistration {
    pub(super) architectures: &'static [&'static str],   // canonical + aliases
    pub(super) chat_template: ChatTemplate,              // id + render fn(s)
    pub(super) stop_markers: &'static [&'static str],    // fallback stop tokens
    pub(super) backends: &'static [(&'static str, BackendLoader)],
    pub(super) family: Option<ModelFamily>,              // native fallback parameters
    pub(super) shaders: &'static [&'static str],         // Vulkan shader names used
}

impl ModelRegistration {
    fn loader_for(&self, backend: &str) -> Option<BackendLoader>;
    fn backend_names(&self) -> impl Iterator<Item = &'static str> + '_;
}
```

### 3.1 `BackendLoader` — one enum, three signatures

Each backend carries the loader signature natural to its data path (this is
why it is an enum and not a single `dyn` fn — the backends materialize
weights in fundamentally different ways):

```rust
#[derive(Clone, Copy)]
pub(super) enum BackendLoader {
    /// Candle: builds tensors from mapped shards through a VarBuilder.
    Candle(for<'a> fn(&[u8], Value, VarBuilder<'a>, &Device)
        -> Result<Box<dyn ModelRuntime>, String>),
    /// Vulkan: receives the aligned shard paths.
    Vulkan(fn(&[PathBuf], &[u8], Value) -> Result<Box<dyn ModelRuntime>, String>),
    /// Native mmap + Ant tiering: prepared directory + residency plan + family.
    Native(fn(&Path, &[u8], &Value, &BTreeMap<String, String>, ModelFamily)
        -> Result<Box<dyn ModelRuntime>, String>),
}
```

Module-level lookups:

```rust
backend_loader_for_architecture(architecture, backend) -> Option<BackendLoader>
registered_backend_names(architecture)                 -> Vec<&'static str>
family_for_architecture(architecture)                  -> Option<ModelFamily>
registration_for_architecture(architecture)            -> Result<&'static ModelRegistration, String>
```

### 3.2 `ModelFamily` — family-level fallback parameters

```rust
pub(super) struct ModelFamily {
    pub(super) rope_theta: f64,
    pub(super) rms_norm_eps: f64,
    pub(super) tie_word_embeddings: bool,
    /// (hidden_size, vocab_size, q_heads, kv_heads, head_dim) per published size
    pub(super) profiles: &'static [(usize, usize, usize, usize, usize)],
    /// Extra config.json fields Candle transformer structs require,
    /// merged into a synthesized config when the directory has none.
    pub(super) extra_config_json: &'static str,
}
```

Purpose and the resolution chain that consumes it:
[ANT_MEMORY.md](ANT_MEMORY.md) §4. Key facts:

- Profiles are keyed by `(hidden_size, vocab_size)` because hidden size alone
  is ambiguous within a family (llama2-7B vs llama3-8B: both hidden 4096, but
  vocab 32000 vs 128256 and kv heads 32 vs 8).
- `extra_config_json` exists because the Candle transformer structs require
  fields (e.g. qwen2's `hidden_act`, `sliding_window`, `max_window_layers`)
  that the native runner does not need — they are merged only when a config
  is synthesized from the manifest.

## 4. Registration file anatomy

`src/chat/models/registrations/qwen2.rs`, annotated section by section:

```rust
//! Header comment: what the file is, where build.rs collects it, and the
//! guarantee that it contains no runtime code.

use super::{BackendLoader, ChatTemplate, ModelRegistration};   // shared types
use super::templates::qwen;                                     // chat template fn
use super::qwen2::load;                                         // Candle impl bridge
#[cfg(feature = "vulkan")]
use super::qwen2::load_vulkan;                                  // feature-gated

/// Exported for the generated ALL_ARCHITECTURES index.
pub(crate) const ARCHITECTURES: &[&str] = &["Qwen2ForCausalLM", "qwen2"];

pub(crate) const REGISTRATION: ModelRegistration = ModelRegistration {
    architectures: ARCHITECTURES,
    chat_template: ChatTemplate { id: "qwen", render: qwen, header_renderer: None },
    stop_markers: &["<|im_end|>"],
    backends: model_backends(),
    family: Some(sha_family()),
    shaders: &["shared_ops"],
};

/// Family constants: fallback inference parameters + published-size profiles.
const fn sha_family() -> super::ModelFamily { ... }        // rope/eps/tie/profiles/extra

/// Backend table: candle always; native and vulkan as registered.
const fn model_backends() -> &'static [(&'static str, BackendLoader)] {
    #[cfg(feature = "vulkan")]
    { &[ ("candle", ...), ("native", ...), ("vulkan", ...) ] }
    #[cfg(not(feature = "vulkan"))]
    { &[ ("candle", ...), ("native", ...) ] }
}
```

Rules:

- Everything is `const`-constructible — registrations are `const` items.
- `#[cfg(feature = "vulkan")]` gates the vulkan backend entry, the
  `load_vulkan` import, and (in implementation files) the function itself.
- fn items coerce to fn pointers inside const initializers
  (`loader: load` style is what makes the table work).

Current registration state (which family registers what):

| Family | Candle | Native | Vulkan | Family constants |
|--------|--------|--------|--------|------------------|
| qwen2  | ✓      | ✓      | ✓*     | ✓ (profiles: 0.5B/1.5B/7B) |
| llama  | ✓      | ✓      | ✓*     | ✓ (profiles: 3.2-1B/3.2-3B/3-8B/2-7B) |
| qwen3  | ✓      | ✓      | ✓*     | ✓ (profiles: 0.6B/1.7B/4B/8B) |
| gemma  | ✓      | —      | ✓*     | — |
| mistral| ✓      | —      | ✓*     | — |
| mixtral| ✓      | —      | ✓*     | — |
| phi    | ✓      | —      | ✓*     | — |

\* when built with `--features vulkan`. A test
(`backend_registration_is_explicit_per_architecture`) asserts this table stays
truthful.

## 5. Backend selection flow (`Engine::load`)

```
CHEETAH_DEVICE (default "cpu")
├── cpu            → backend_loader_for_architecture(arch, "native")?
│       ├── Some(Native(loader)) → loader(model_dir, config, raw, plan, family)
│       └── None                 → guidance error ("no native CPU backend registered;
│                                    Candle CPU path is retired; use cuda/metal")
├── cuda / metal   → Candle loader (device from the candle backend factories)
└── vulkan         → loader_for("vulkan") → executor; on failure an explicit
                     error (never a silent CPU fallback)
```

Selection details worth knowing:

- The native branch requires `family_for_architecture` to resolve — a
  registration that declares a native backend without family constants is a
  build-time inconsistency caught by test.
- `CHEETAH_NATIVE=0` historically forced the Candle CPU path; since the CPU
  path retirement it simply selects nothing (the guidance error explains the
  options). The internal Candle loader remains available to tests as the
  numerical oracle.
- The startup banner prints the registered backend list per architecture
  (`backends: candle, native`), which is the quickest way to validate a
  registration change.

## 6. Backend implementations and their data paths

| Backend | Implementation | Weight data path |
|---------|----------------|------------------|
| Candle | `candle.rs` (`VarBuilder::from_mmaped_safetensors`, F32) + per-architecture wrappers around `candle_transformers` | owned tensors, materialized at build (CUDA/Metal devices only) |
| Native | `native/` (mmap store, Ant tiers, SIMD kernels) | zero-copy mmap views in stored dtype; tiers = real pages |
| Vulkan | `vulkan_transformer.rs` executors (transformer + Phi) + `cheetah_vulkan.c` substrate | weights staged into a VRAM-allocator pool; HOST_VISIBLE|HOST_COHERENT heap required |

The runtime boundary is backend-agnostic: `ModelRuntime::forward(&[u32],
usize) -> Result<Vec<f32>, String>` — tokens in, final-position logits out.
No Candle type crosses it (Candle runtimes convert internally; the Vulkan
executor is Candle-free; the native runner is Candle-free).

`ModelRuntime` also exposes `as_ant_tier_control` — the native runtime
returns its `AntTierControl` so the engine's Ant hooks act on real pages
(see [ANT_MEMORY.md](ANT_MEMORY.md) §7.4); other backends return `None` and
keep metadata-only bookkeeping.

## 7. Tests guarding the registry

In `src/chat/models/candle.rs` (tests module):

- `registers_architecture_names_and_aliases` — every canonical name and alias
  resolves through `registration_for_architecture`.
- `registrations_include_chat_metadata` — non-empty architectures/stop
  markers; chat template ids for representative families (looked up through
  the registry, not file paths, so the test survives file reorganizations).
- `vulkan_loader_registration_matches_compiled_support` — every registration
  has a candle backend; vulkan entries match the compiled feature.
- `backend_registration_is_explicit_per_architecture` — qwen2/llama/qwen3
  must register native (+ family constants), the other families must not;
  lookup helpers behave.
- `all_architectures_index_covers_the_registry` — `ALL_ARCHITECTURES` ↔
  `REGISTRY` consistency in both directions, and every indexed name
  resolves.

When you add or retire a backend registration, update
`backend_registration_is_explicit_per_architecture` — it is the contract
that keeps the table in §4 honest.

## 8. How to add things

### 8.1 A new architecture (Candle-only)

1. Create `src/chat/models/<name>.rs` with the runtime (Candle wrapper:
   `Runtime { model, device }`, the backend-agnostic `forward` bridge, loader)
   — see the existing files for the pattern (llama shows a KV-cache-carrying
   model, phi shows a no-cache model).
2. Add `mod <name>;` to `src/chat/models/mod.rs`.
3. Create `src/chat/models/registrations/<name>.rs` (architectures, template,
   stop markers, `backends: candle-only`, `family: None`).
4. Extend `backend_registration_is_explicit_per_architecture` accordingly.

### 8.2 A new native family

1. Implement the forward deltas in the native runner
   ([ANT_MEMORY.md](ANT_MEMORY.md) §11 checklist).
2. In the family's registration file: add the native backend entry to
   `model_backends()` and fill `family` (constants + full profile table).
3. Extend the synthetic decoder generator for the structural deltas and add
   the native-vs-candle comparison test.
4. Flip the assertion test to include the family.

### 8.3 A new backend kind

1. Add a `BackendLoader` variant with the loader signature natural to the
   backend's data path.
2. Add selection logic in `Engine::load` (or `registry.rs`).
3. Add the backend-name assertions to the registry tests.
4. Document the data-path contract in [ANT_MEMORY.md](ANT_MEMORY.md) §6 or a
   sibling section.

### 8.4 A Vulkan model executor

Vulkan executors are not generated from registrations — a registration
declares the loader and the shaders it needs; the executor implementation
(`vulkan_transformer.rs`) owns the actual compute graph. Follow
`VulkanTransformerExecutor` (transformer + Phi variants) and keep the
executor Candle-free (the shared shader library lives in `*.comp` at the repo
root; the shader registry maps names to compiled artifacts under the feature).

## 9. Design decisions worth remembering

1. **Declarative files + directory-as-contract.** The first design scanned the
   whole `models/` directory with a hand-maintained exclusion table
   (`mod|candle|registry|templates`) — every new infrastructure file required
   a build.rs edit, and the registration lived inside 500-line
   implementation files. The dedicated `registrations/` directory removed the
   exclusion table and separated WHAT from HOW.
2. **Vocab-keyed profiles.** Hidden size alone is ambiguous within a family
   (llama2-7B vs llama3-8B); the profile key is `(hidden, vocab)`.
3. **Backend table instead of loader fields.** Three parallel `Option<fn>`
   fields (loader/vulkan_loader/native_loader) meant every new backend
   touched all model files. The `backends` table makes a backend a one-line
   declaration and a single enum variant.
4. **Backend-agnostic runtime boundary.** `forward(&[u32]) -> Vec<f32>` keeps
   the engine core free of Candle types, which is what allows Candle to be
   narrowed to CUDA/Metal while native and Vulkan stay independent.
5. **Candle CPU path retirement.** The Candle CPU backend is retired
   (explicit guidance error) — CPU belongs to native, Candle remains the
   CUDA/Metal option, and the internal Candle loader survives as the tests'
   numerical oracle.
